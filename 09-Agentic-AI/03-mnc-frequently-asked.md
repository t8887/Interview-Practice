## RAG (Retrieval-Augmented Generation)

### Q1: What is RAG? Why is it needed?
> **A:** RAG combines retrieval (search) with generation (LLM). Instead of relying on LLM's training data alone:
> 1. **Retrieve** relevant documents from a knowledge base
> 2. **Augment** the prompt with retrieved context
> 3. **Generate** answer grounded in actual data
> **Why:** Reduces hallucinations, keeps answers up-to-date, works with private data, no need to fine-tune.
> ```
> User Query → Embedding → Vector DB Search → Top-K Docs → LLM (query + docs) → Answer
> ```

### Q2: What are embeddings? How do vector databases work?
> **Embeddings:** Dense numerical vectors that capture semantic meaning.
> - "king" and "queen" are close in vector space
> - Generated by models: OpenAI `text-embedding-3-small`, Cohere, sentence-transformers
>
> **Vector DB:** Stores embeddings and enables similarity search (cosine similarity, dot product).
> | Vector DB | Key Feature |
> |-----------|------------|
> | **Pinecone** | Managed, serverless |
> | **Weaviate** | Open-source, hybrid search |
> | **ChromaDB** | Lightweight, local dev |
> | **pgvector** | PostgreSQL extension |
> | **Qdrant** | High performance, Rust-based |

### Q3: How do you chunk documents for RAG?
> | Strategy | Description |
> |----------|------------|
> | **Fixed size** | 500-1000 tokens with overlap (200 tokens) |
> | **Semantic** | Split by paragraphs/sections, respect document structure |
> | **Recursive** | Try splitting by `\n\n` → `\n` → `. ` → ` ` |
> | **Sentence-level** | Each sentence = chunk (for precise retrieval) |
> **Best practice:** Recursive with overlap. Chunk size depends on model context window and retrieval precision trade-off.

### Q4: How do you evaluate RAG quality?
> | Metric | What it measures |
> |--------|-----------------|
> | **Faithfulness** | Is the answer grounded in retrieved context? |
> | **Answer relevancy** | Does the answer address the question? |
> | **Context precision** | Are retrieved docs relevant? |
> | **Context recall** | Were all needed docs retrieved? |
> Tools: RAGAS framework, LangSmith, custom LLM-as-judge evaluations.

### Q5: What is the difference between naive RAG and advanced RAG?
> | Naive RAG | Advanced RAG |
> |-----------|-------------|
> | Single retrieval step | Multi-step retrieval |
> | Basic chunking | Hierarchical / semantic chunking |
> | No reranking | Reranking retrieved results (Cohere reranker) |
> | Single query | Query expansion / HyDE (hypothetical doc embeddings) |
> | No metadata | Metadata filtering (date, source, category) |

## AI Agents

### Q6: What is an AI agent? How is it different from a chatbot?
> | Chatbot | AI Agent |
> |---------|---------|
> | Responds to input | Plans, decides, acts autonomously |
> | Single turn or simple multi-turn | Multi-step reasoning with tool use |
> | Pre-defined flows | Dynamic action selection |
> | No external actions | Can call APIs, search web, write code |
>
> **Agent loop:** Observe → Think → Act → Observe (repeat until goal achieved)

### Q7: What is the ReAct pattern?
> **ReAct** = **Re**asoning + **Act**ion. The agent alternates between:
> 1. **Thought:** Reason about what to do next
> 2. **Action:** Call a tool (search, calculate, API call)
> 3. **Observation:** Process tool output
> 4. Repeat until task is complete
> ```
> Thought: I need to find the current weather in Mumbai
> Action: search_weather(location="Mumbai")
> Observation: 32°C, partly cloudy
> Thought: I have the answer
> Final Answer: The weather in Mumbai is 32°C and partly cloudy.
> ```

### Q8: What are tool/function calling capabilities in LLMs?
> **A:** LLMs can be given a list of available tools (functions with descriptions + parameters). The model decides:
> - **Which tool** to call
> - **What arguments** to pass
> The application executes the tool and returns results to the LLM.
> ```json
> {
>   "name": "get_order_status",
>   "description": "Get the status of a customer order",
>   "parameters": {
>     "type": "object",
>     "properties": {
>       "order_id": { "type": "string", "description": "The order ID" }
>     }
>   }
> }
> ```
> **Where asked:** Any company building AI features

### Q9: What is the difference between single-agent and multi-agent systems?
> | Single Agent | Multi-Agent |
> |-------------|------------|
> | One LLM handles everything | Specialized agents collaborate |
> | Simpler | Complex orchestration |
> | Good for straightforward tasks | Good for complex workflows |
> Examples of multi-agent: Researcher + Writer + Reviewer, Code Generator + Test Writer + Code Reviewer

## Frameworks

### Q10: Compare LangChain, LlamaIndex, and CrewAI.
> | Framework | Best for |
> |-----------|---------|
> | **LangChain** | General-purpose agent framework, chains, tools, memory |
> | **LlamaIndex** | Data indexing & RAG (best for document Q&A) |
> | **CrewAI** | Multi-agent collaboration with roles |
> | **AutoGen** | Multi-agent conversations (Microsoft) |
> | **Semantic Kernel** | Enterprise AI orchestration (.NET/Python) |

### Q11: What is LangChain? Key components?
> - **LLM/Chat Models:** OpenAI, Anthropic, Ollama wrappers
> - **Prompts:** Templates, few-shot, output parsers
> - **Chains:** Sequential LLM calls (LCEL = LangChain Expression Language)
> - **Agents:** ReAct, tools, function calling
> - **Memory:** Conversation buffer, summary, vector store
> - **Retrievers:** Vector store, BM25, ensemble, multi-query

### Q12: What is LangGraph?
> **A:** Framework for building **stateful, multi-step** agent workflows as graphs.
> - Nodes = agent steps (LLM calls, tool use, conditions)
> - Edges = transitions between steps
> - Built-in state management, checkpointing, human-in-the-loop
> - Better than chains for complex workflows with branching/looping

## Production AI

### Q13: How do you handle hallucinations in production?
> 1. **RAG** — ground responses in retrieved data
> 2. **System prompts** — "Only answer from provided context"
> 3. **Output validation** — check against known facts/schema
> 4. **Confidence scoring** — LLM self-evaluation
> 5. **Citation requirement** — force model to cite sources
> 6. **Guardrails** (NeMo Guardrails, Guardrails AI) — check output before returning
> 7. **Human-in-the-loop** for high-stakes decisions

### Q14: How do you monitor and evaluate LLM applications?
> | Tool | Purpose |
> |------|---------|
> | **LangSmith** | Trace chains/agents, debug, evaluate |
> | **Weights & Biases** | Experiment tracking, prompt versioning |
> | **Phoenix (Arize)** | LLM observability, trace visualization |
> | **Custom logging** | Log prompts, responses, latency, token usage, costs |
> **Key metrics:** Latency (TTFT, total), token usage, cost per query, user satisfaction, factual accuracy.

### Q15: What are prompt engineering best practices?
> 1. **Be specific** — clear instructions with examples (few-shot)
> 2. **Role assignment** — "You are a senior backend engineer..."
> 3. **Chain-of-thought** — "Think step by step"
> 4. **Output format** — specify JSON schema, markdown structure
> 5. **Negative examples** — "Do NOT include..."
> 6. **Temperature tuning** — 0 for factual, 0.7+ for creative
> 7. **Structured output** — use function calling / JSON mode for reliable parsing

## Architecture Questions

### Q16: Design a customer support AI system.
> ```
> User Message → Intent Classification → Router
>                                          |
>             +----------------------------+----------------------------+
>             |                            |                            |
>      Simple FAQ (RAG)          Order Query (Tool Call)        Escalation (Human)
>             |                            |                            |
>       Vector Search +             API: get_order_status         Transfer to Agent
>       LLM Generate                API: track_shipment          (with context)
> ```
> - **Guardrails:** Don't share other customers' data, don't make promises
> - **Memory:** Conversation history for context
> - **Evaluation:** Customer satisfaction, resolution rate, escalation rate

### Q17: How do you handle rate limits and costs with LLM APIs?
> 1. **Caching** — cache identical prompts (semantic cache with embeddings)
> 2. **Tiered models** — GPT-4 for complex, GPT-3.5/Haiku for simple
> 3. **Token budgeting** — truncate context, summarize history
> 4. **Rate limiting** — queue requests, exponential backoff
> 5. **Batch processing** — group non-urgent requests
> 6. **Self-hosted models** — Ollama, vLLM for high-volume use cases

### Q18: What is fine-tuning vs RAG? When to use which?
> | Fine-tuning | RAG |
> |------------|-----|
> | Teaches model new behavior/style | Provides model with current data |
> | Expensive (training compute) | Cheaper (retrieval infra) |
> | One-time (needs retraining for new data) | Dynamic (update knowledge base anytime) |
> | Good for: tone, format, domain jargon | Good for: factual Q&A, docs, search |
> **Rule:** Try RAG first. Fine-tune only if RAG can't achieve the desired behavior/style.

## Quick Fire

### Q19: What is a context window? Why does it matter?
> **A:** Maximum tokens (input + output) an LLM can process. GPT-4o: 128K, Claude: 200K, Gemini: 1M+. Matters because: larger context = more retrieved docs, but higher cost + latency. Stuffing everything into context isn't always better (lost in the middle problem).

### Q20: What is MCP (Model Context Protocol)?
> **A:** Anthropic's open standard for connecting AI models to external data sources and tools. Provides a standardized way for agents to discover and use tools, similar to how USB-C standardized device connections. Key benefit: build tool integrations once, use with any MCP-compatible model/agent.
